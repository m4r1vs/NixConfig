# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

**Never commit anything.** Leave all git commits to the user.

## Repository Overview

Multi-platform Nix flake configuring NixOS, nix-darwin, and WSL hosts with home-manager. Stable nixpkgs (`nixos-26.05`) is the base; selected packages come from unstable or overlays.

## Commands

- `rebuild` — script in PATH on every host; runs `sudo nixos-rebuild switch` or `sudo darwin-rebuild switch` for the current host and re-applies the active specialisation (read from `/etc/nixos_active_specialisation`).
- `sudo nixos-rebuild switch --flake ~/NixConfig/#<host>` — manual equivalent.
- `nixos-rebuild build --flake .#<host>` — build without switching (useful to verify a config change evaluates and compiles).
- `nix build .#packages.x86_64-linux.bootstrap_local_x86_64` / `.#packages.aarch64-linux.bootstrap_remote_arm64` — build install ISOs.
- `nix flake check` — runs the pre-commit hooks and `eval-hosts`, which evaluates every host of the current system (a host that stops evaluating fails the check). Works on Linux; from darwin use `nix build .#checks.aarch64-darwin.{eval-hosts,pre-commit-check}`, since falkenberg (`hosts/kubenix/kubernetes.nix`) needs an aarch64-linux build during evaluation.
- Format Nix files with `alejandra` (the formatter used throughout this repo).

## Architecture

### systemArgs threading

Every host in `flake.nix` defines a `systemArgs` attrset (username, git identity, hostname, `theme` from `makeTheme.nix`, platform, and for servers ipv4/domain). It is injected via `config._module.args` and is available as the `systemArgs` argument in **every** NixOS, darwin, and home-manager module.

### Host kind (`configured.host`)

`hosts/host.nix` defines read-only `configured.host.*` flags derived from existing options: `kind` (desktop/server/wsl/iso/darwin; ISOs set it explicitly), `windowManager` (per specialisation), and `isDesktop`, `isServer`, `isWSL`, `isISO`, `isDarwin`, `isGraphical`, `isHeadless`, `isDev`, `isWayland`, `isX86`, `hasPowerProfiles`, plus `flakePath` (the checkout used by nh/rebuild). `isDev` defaults to every graphical or WSL host and is the one flag a host may set (downstream hosts set it to false). Use these instead of recomputing platform checks. Home-manager modules and scripts get them as the `host` argument; NixOS/darwin modules read `config.configured.host`. Never derive them from `pkgs` (nixpkgs.nix reads them inside the overlay).

### Auto-imported modules + `configured.*` enable options

`nixos-modules/default.nix` and `home-manager/modules/default.nix` automatically import every sibling `.nix` file and every subdirectory (its `default.nix`). Consequences when adding a module:

1. Create the file — **no import registration needed**.
2. The module **must** gate its config behind a `mkEnableOption` (`options.configured.*`, `options.programs.configured.*`, or `options.services.configured.*`) with `config = mkIf cfg.enable {...}`. Without this it applies unconditionally to all hosts.
3. Enable it per-host in `hosts/<host>/default.nix` (NixOS options) or in `home-manager/home.nix` (home-manager options, keyed off `host.isDesktop` / `host.isDev` / `host.isDarwin` etc.).

### Scripts system

`home-manager/scripts/*.nix` each export an attrset of script derivations. `home-manager/makeScripts.nix` auto-collects them into one fixpoint (duplicate names fail evaluation) and passes it as the `scripts` argument to every home-manager module (via `extraSpecialArgs`). Reference a script as `${scripts.<name>}`; scripts can reference each other through the same `scripts` argument.

Script files also receive `helpers` from `home-manager/scriptLib.nix`: prefer `helpers.mkScript { name; text; runtimeInputs; }` for new scripts (strict bash + build-time shellcheck; `$out` is the script file, so `${scripts.x}` keeps working), `helpers.playSound "clipboard"` for system sounds and `helpers.clipboard.copy`/`.paste` for the session's clipboard. Older scripts still use `pkgs.writeShellScript`; migrate them one at a time.

### Hosts (`flake.nix` + `hosts/`)

- `worknix`, `nixpad`, `desknix` — graphical x86 workstations (Hyprland).
- `nixner` — aarch64 Hetzner server (comin GitOps, homepage, binary cache, DNS; server services live in `nixos-modules/server/`).
- `kubenix` — Kubernetes node fleet, generated by `hosts/kubenix/default.nix`.
- `winix` — NixOS on WSL. `nixbook` — macOS via nix-darwin (`hosts/darwin/`). `yannix` (the laptop of another user) lives in its own repository, see "Downstream hosts".
- `hosts/nixos.nix` is shared by all NixOS hosts; `hosts/default.nix` + `nixpkgs.nix` are shared by everything including darwin.

### Downstream hosts

A host can live in its own repository that has this flake as its only input and calls `lib.mkHost` (defined in `flake.nix`). yannix does: a non-developer's laptop that follows `main` through its daily auto-upgrade, so whatever lands on `main` reaches it within a day. Its owner cannot edit anything here; he overrides from his side. `examples/downstream` is a stand-in with the same shape and is evaluated by `eval-hosts`.

That makes these a public interface. Keep them working, or change `examples/downstream` and the downstream repository in the same go:

- the arguments of `lib.mkHost` (`hostname`, `username`, `git`, `theme`, `system`, `modules`, `extraArgs`);
- `configured.host.isDev`, `configured.i3.scaling`, `configured.laptop.{enable,chargeLimit}`, `configured.limine.secureboot`, `configured.tpmUnlock.{volumeKeyId,resumeOffset}`;
- `programs.configured.browser.{default,side,secondaryProfile}`, `programs.configured.hyprland.{startupApps,umlautBinds,maxVolume,powerMenuExit}`, `programs.configured.hyprlock.scaling`, `services.configured.auto-upgrade.schedule`;
- the shape of `wayland.windowManager.hyprland.settings` (`bind` entries with `_args`, `monitor`, `window_rule`, `workspace_rule`, `on`) and `programs.waybar.settings.mainBar`, which downstream hosts extend.

When adding something that is about development, work or personal habits (a keybind, a Waybar module, an autostarted app), put it behind `host.isDev` or an option, so it does not show up on a downstream host.

### Browser

`home-manager/modules/browser.nix` picks the browsers by role: `programs.configured.browser.default` (opens links, launcher entries, workspace 1) and `.side` (special workspace on F12). Modules and scripts read `programs.configured.browser.resolved` (command, window class, process name, profiles) and never name a browser package themselves.

### Hardware settings

What every graphical machine gets lives in `nixos-modules/desktop.nix` (firmware updates, SSD health, earlyoom, NVMe scheduler, btrfs scrub defaults, BBR). What only a battery-powered machine wants lives in `nixos-modules/laptop.nix` behind `configured.laptop.enable` (power-profiles-daemon with UPower, zswap, optional `chargeLimit`). A host file keeps only what is specific to that model (drivers, kernel quirks, face unlock), so a new improvement that is not tied to one model goes into one of the two modules.

### Disk unlock

`nixos-modules/tpm-unlock.nix` turns on TPM unlock of `cryptroot` wherever `configured.limine.secureboot` is set, and pins what the initrd trusts before the disk opens: the volume key (`configured.tpmUnlock.volumeKeyId`) and the hibernation resume location (`.resumeOffset`). Both are per-host values read on the machine itself; background and procedure in `TPM_HARDENINGS.md`. Its initrd runs a patched systemd (`fixate-header-check.patch`) so the pin also covers the LUKS2 header; the patch has to keep applying to the systemd nixpkgs ships.

### Desktop specialisations

`nixos-modules/desktop.nix` defines `configured.desktop.windowManagers.{hyprland,i3,gamescope}` as NixOS specialisations with one marked default. The `rebuild` script keeps the active specialisation across rebuilds.

### Overlays and unstable packages

All overlays live in `nixpkgs.nix`: own flake-input packages (atai, golazo, …), custom font derivations from `assets/fonts/`, and packages pulled from `nixpkgs_unstable` via `pkgsUnstable`. Prefer adding version overrides there rather than in individual modules.

### Theming

`makeTheme.nix` maps primary/secondary color names to hex/RGB; each host picks its pair in `flake.nix` and modules read colors from `systemArgs.theme`. Runtime palette switching (dark/light, per-wallpaper) is handled by the `custom-wallpaper-theme` script writing `~/.theme/palette.json`.

### NeoVim

Plugins are managed by lazy.nvim, not nixpkgs; the lazy lockfile is tracked in `home-manager/modules/neovim/nvim/` so plugin updates show up in git.
